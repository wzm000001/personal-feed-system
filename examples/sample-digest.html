OpenAI Codex 推出 Appshots

按下 Command-Command，AI 看见你正在看的整个屏幕 —— context 抓取从"用户描述"进化到"AI 主动捕获"。

👤 Sam Altman + @OpenAIDevs 📱 X ⏱ 数小时前 ❤️ 5.7K · 👁️ 1.2M 📖 3 分钟

🔍 这条在讲什么

OpenAI 给 Codex（他们的 AI coding agent，对标 Claude Code）推出新功能 Appshots：

  • Mac 上按 Command-Command 把当前 app 窗口附到 Codex 对话
  • Codex 拿到 截图 + 窗口文本（含屏幕外没滚动到的内容）
  • Mac 所有 plan 可用，Enterprise 即将支持
— 工作流对比 —
😩
没有 Appshots 时
打开 Notion 看 PRD → 截图 → 粘贴到 AI → 描述上下文 → AI 看不清又问 → 复制更多文字...
⚡
有了 Appshots
看着 Notion PRD → Cmd+Cmd → Codex 已经知道你看什么了 → 直接帮你写代码

💎 价值点（为什么重要）

这是 AI coding agent 的 context UX 革命：

  • 过去：Cursor / Claude Code 一直在"读 codebase"
  • 现在："读你屏幕上正在看的应用"是新维度
  • 意味着 AI agent 从「项目内助手」扩展到 「桌面级助手」

🧠 引发的思考（结合你的处境）

  1. Claude Code 会跟进吗？ Anthropic 已有 Claude in Chrome（你已配对）但只读浏览器。Mac 桌面级 context 抓取是下一步必然
  2. 对你 data-bp 项目的影响：你常在 VSCode + 数据仪表盘 + 业务文档间切换。如果 AI 能一键抓任意窗口，data-bp"业务背景 → 代码"的传递成本归零
  3. 隐私边界：屏幕外内容也被抓 = 你看不到的内容也进 LLM。要警惕

想象下次让 Claude Code 改 data-bp 代码时，能像 Appshots 一样把"业务方在 Notion 写的 PRD"一键附上。这个 PRD 当前是怎么传递给 AI 的？这一步的 friction 是多少？

测试理解

假设你在 VSCode 看 data-bp 代码，同时在 Notion 看 PRD，想让 Claude Code 改代码符合 PRD。**现在你最快传递 PRD 的方式是什么？这个流程有几步？**

典型现在流程（5+ 步）：切到 Notion → Cmd+A 全选 → 复制 → 切到 VSCode → 粘贴给 Claude Code → 描述"这是 PRD"

有 Appshots 后（1 步）：看着 Notion → Cmd+Cmd → AI 已经懂了

启发：Claude Code 没这功能 = 你的 friction 仍然是 5+ 步。考虑：①写个 AppleScript 自动化复制 ②等 Anthropic 跟进 ③把常用 PRD 类型做成 skill 模板

AI 模型成本走向"分层"，不会收敛

Box CEO: AI chat tools 小 context 时代结束，agents 巨大 context + long-running work 把推理成本拉高一个数量级 —— 企业需要新角色管理多模型成本。

👤 Aaron Levie · Box CEO 📱 X ⏱ 8 小时前 ❤️ 474 · 🔁 48 · 💬 67 📖 4 分钟

🔍 这条在讲什么

📊 过去预期
模型同质化 → 价格趋同 → 成本收敛到单一低价 per token
⚡ 实际发生
模型能力分层 → 成本反向 stratification（分层） → 差距越拉越大

三个核心变化：

  1. AI chat tools（小 context、便宜）→ AI agents（巨大 context + long-running + 推理成本 ×10）
  2. Frontier 任务（coding、science、finance、consulting）继续吃贵的 frontier 模型
  3. 常规任务下沉到便宜模型（Haiku、GPT-mini），但同一工作流多模型混用

💎 价值点

这是 enterprise AI 部署的真实瓶颈 —— 不是模型能力，是多模型成本治理。Box 是企业 SaaS 直接看到客户用 AI 时成本爆炸的真实故事。原本"全用 GPT-4"的简单选型，变成"50 个任务每个该用什么模型"的细颗粒决策。

🧠 引发的思考（结合你的处境）

  1. data-bp 项目 100% 命中：它是 enterprise AI。「业务知识页」生成属于 frontier 任务（需要 Sonnet 4 的推理）还是常规任务（Haiku 就够）？
  2. vault topics/ai-coding-agents 缺这一层：你之前关注"用什么 AI 工具"，但 Aaron 的视角是"**工作流里多个模型怎么编排**"
  3. 副业机会信号：「企业 AI 多模型成本管理」是未填满的工具空白 —— 你想做的副业方向之一

把 data-bp 核心工作流拆成 5-10 个子任务，每个问：「**这步需要 Sonnet 4 的智能，还是 Haiku 就够？**」这个拆解动作本身就是 Aaron 说的 "new finance team" 角色。

测试理解

data-bp 项目典型工作流可能涉及：①读业务文档 ②抽取关键指标 ③生成知识页结构 ④填充内容 ⑤生成 SQL 查询。**请用 1-5 各打分（1=Haiku 就行 / 5=必须 Sonnet 4），并说明 1 个理由。**

参考答案（你的判断可能不同）：

  • ①读业务文档 = 2（结构化提取，Haiku/小模型即可）
  • ②抽取关键指标 = 3-4（需要业务理解，但任务边界清晰）
  • ③生成知识页结构 = 5（需要 reasoning + taste，必须 Sonnet 4）
  • ④填充内容 = 3（按 schema 填，中等模型）
  • ⑤生成 SQL 查询 = 4-5（复杂 join 时需要 reasoning，但简单查询 3 就够）

启发：这个拆解 + 模型映射就是你 data-bp 项目缺的「成本架构层」。可以尝试在 vault 写一个 concepts/cost-stratification.md。

Import AI 457：AI Stuxnet + Positive Alignment

Anthropic 联创 Jack Clark 周报：AI 训练管道本身是新攻击面（"AI Stuxnet"），且 alignment 范式从"防止做坏"升级到"主动做好"。

👤 Jack Clark · Anthropic 联合创始人 📧 Newsletter ⏱ 4 天前 📖 8 分钟

🔍 这条在讲什么

Jack Clark（Anthropic 政策灵魂人物之一）457 期周报，三件大事：

AI 风险地图 · 从训练管道到策略层，每一层都是工程面
  1. AI Stuxnet（隐喻命名）：用软件破坏 AI 训练里的精确数值计算，让模型"看似正常"地学到错的东西 —— 类似 2010 年 Stuxnet 病毒精确攻击伊朗核设施离心机
  2. Cursed Muon Optimizer：优化器层面发现新漏洞，可通过精心构造的训练样本污染模型
  3. Positive Alignment：超越传统 AI safety（防止 AI 做坏）的范式 → "让 AI 主动做好"

💎 价值点

这是 Anthropic 战略灵魂的"系统级 AI 风险地图"。让你看到：

  • AI 基础设施层（训练 pipeline、optimizer）也是攻击面，不只是 prompt injection
  • Alignment 从被动转向主动 = AI 工程范式升级
  • 政策视角 vs 工程视角的桥梁

🧠 引发的思考（结合你的处境）

  1. 你做 data-bp 是 enterprise data project，业务数据本身就是攻击面 —— "AI Stuxnet" 思路放到企业场景：恶意构造的业务 metric 会让 AI 知识页学错吗？
  2. Positive vs Safety = AI 工程"防御 vs 价值创造"范式分野。你做 AI 落地是哪个范式？
  3. "前 10%" 必读 Jack Clark：Import AI 是 AI 圈最重要的 newsletter 之一，Anthropic 联创视角，每周一期

读这一期时不要只看技术细节，重点理解 Jack 怎么把 AI 风险按「训练 / inference / 部署 / 策略」分层。这种**系统级思维**才是顶级 AI builder 区别于普通工程师的核心。

测试理解

你 data-bp 项目里"业务知识页生成"的攻击面，**按训练/inference/部署/策略 4 层分别是什么**？

参考答案（你的实际项目可能不同）：

  • 训练层：knowledge base 历史数据污染（错误业务定义被模型"学"进去）
  • Inference 层：prompt injection（业务方在 PRD 里塞恶意指令）
  • 部署层：知识页生成后被错误使用（业务决策依赖错的知识）
  • 策略层：你团队对"什么算正确的知识"没共识 → AI 学到的是混乱的

启发：写一个 concepts/ai-attack-surface.md 把这 4 层映射到 data-bp 具体文件 / 代码位置。

Anthropic: 把 Agent 的"大脑"和"双手"解耦

brain (模型 + harness) 与 hands (sandbox + tools) 通过协议解耦，独立失败恢复、独立扩展 —— 这是 Claude Code / Skills 系统的设计哲学。

👤 Anthropic Engineering 📄 Engineering Blog ⏱ 44 天前 ⭐ Evergreen 白名单 📖 10 分钟

🔍 核心抽象：Brain ↔ Hands

Brain / Hands 解耦 · 通过协议通信 · 两边可独立失败、独立扩展

🔧 6 个工程问题（按 Anthropic 处理顺序）

  1. Harness 假设会过时：模型变强后老 harness 反而成瓶颈 → 抽象层要前瞻设计
  2. 避免容器变"宠物"：单容器全栈耦合 → 出问题不知道是模型 bug 还是工具 bug
  3. 凭证与代码隔离：sandbox 里不能有 API key，模型生成的代码可能误用
  4. 长任务上下文外移：session 日志不能塞 context window，必须有外部存储
  5. 多 brain 多 hands：未来一个用户同时跑多个 Claude instance
  6. TTFT 优化：首个 token 时间（Time To First Token）是 UX 核心

💎 价值点

这是当前 AI agent 工程的 SOTA 设计 —— 而且是 Anthropic 自家 Claude Code / Skills 系统的灵魂。

⚡ 你的认知融合机会
你 vault concepts/tool-stack-layering.md 5 层模型（API / CLI / MCP / Skill / Plugin）+ Anthropic brain/hands 二分法 = 完整 agent 工程认知。两个抽象组合形成的二维图，就是 agentic-systems-theory 从 low → medium → high 需要的核心 source。

🧠 引发的思考

  1. brain/hands 映射到 data-bp：业务知识页生成 = brain 侧（决策）；数据接入、SQL 执行 = hands 侧（机械动作）。中间通过什么协议解耦？这就是你应重点设计的
  2. 你 fork 的 llm-wiki-compiler 也是 long-running agent app：hook 是 brain 还是 hands？
  3. 副业方向：基于 brain/hands 抽象做"Agent 部署管理工具"是空白市场（参考 Modal、Replicate）

读时实时把每一节映射到一个你接触过的 AI 工具（Claude Code、weread-skills、llm-wiki-compiler）。如果某节映射不出来，那就是你的认知盲区 —— 重点啃这一节。

测试理解

你 fork 的 llm-wiki-compiler 里，**hook 系统**是 brain 还是 hands？为什么？你做的 3 个 bug 修复涉及 brain 还是 hands？

参考答案：

  • hook 系统：是 hands 侧（具体执行：检测文件变化 → 触发 compile）
  • 但 hook 的"决定是否报 stale"：是 brain 侧（推理"这个状态算不算 stale"）
  • 你 3 个 bug：
    • hook stale 修复：hands 层（时间戳计算 bug）
    • /distill 命令：brain 层（决定"对话要不要 distill"）
    • 路径 docs：纯文档（不在 brain/hands 框架）

启发：vault 里写 concepts/brain-hands-mapping.md，把你接触的所有 AI 工具都映射一遍。

Simon Willison: 编程语言变得"可互换"

AI coding agents 让跨语言重写一个项目从 5+ 年精通门槛降到 1-2 小时 —— 技术决策权重下降，业务/架构决策权重上升。

👤 Simon Willison · Django 联合创始人 📄 个人博客 ⏱ 8 天前 📖 3 分钟

🔍 这条在讲什么

📜 过去
学一门语言到精通 = 5+ 年
→ "Java 12 年" 是稀缺资源
→ 语言锁定（lock-in）严重
⚡ 现在
AI agent 跨语言重写一个项目 = 1-2 小时
→ 编程语言成"可互换"（fungible）
→ 业务/架构决策成核心

💎 价值点

Simon Willison 是 AI 应用领域最权威的个人观察者。他的判断：

  • 极度务实（不炒作）
  • 一手实验（他自己每天用 AI 写代码）
  • 长时间一致（2022 年就在写 LLM 应用观察）

"语言可互换"如果成立，对软件工程职业路径的影响是核心级。

🧠 引发的思考

  1. 你是大数据开发工程师，技能栈 Spark / Flink / Python / Scala / SQL。哪些是"语言锁定" 哪些是"工具锁定"？工具锁定不容易被 AI 替换
  2. 副业方向反思：做 AI 副业，专精一门语言 vs 理解多语言 + 业务？Simon 暗示后者
  3. "前 10%" 的 AI 时代 = 不是某门语言的高手，是能用 AI agents 跨多语言切换 + 设计跨栈系统的人

读完问自己「如果我今天的技能让 AI 来做，我能多快做完同样的工作？」这个比例 = 你被 AI 替代的速度。然后问「我应该升级到 AI 做不了的什么层级？」

测试理解

把你工作里 5 个常见任务，按"AI 能替代的程度"打分（1=不能替代 / 5=完全可替代），并选出 1 个 AI 做不了的事，**作为你下半年要投入的方向**。

参考思路（大数据工程师）：

  • 写 Spark/Flink 作业 = 4（AI 现在写得很好）
  • SQL 优化 = 3-4（中等复杂度 AI 行）
  • 调度 + 监控 = 3（工具锁定，半 AI 替代）
  • 跨团队需求沟通 = 1（人际 + 业务深度）
  • 判断"什么数据值得收集" = 1（业务直觉 + 战略）

AI 做不了的事：跨团队对齐 + 数据战略决策 → 这是你应该深耕的方向。启发：副业方向可以选"教大数据团队如何用 AI" 而不是"写更多 ETL"。
